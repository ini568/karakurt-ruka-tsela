# Публикация «КАРАКУРТ: Рука цела»

Это инструкция для **существующего** статического проекта: точка входа — `index.html`, модули и стили — `src/`. Backend, API, установка npm-зависимостей и сборщик не нужны. Графика рисуется Canvas, звук синтезируется Web Audio; отдельных медиафайлов в текущем графе загрузки нет.

**Наличие этих файлов или готового `dist/` не означает состоявшуюся публичную публикацию.** Настоящий адрес появляется только после успешного deployment. В этой инструкции нет подтверждённой публичной ссылки. `localhost`, локальный путь, шаблон адреса и ссылка на GitHub-репозиторий не заменяют ссылку на работающую игру.

## 1. Подготовка локального артефакта

Нужен Node.js; workflow использует Node.js 22. Из корня проекта:

```text
node tools/prepare-pages.mjs
node tests/regression/publish/artifact.mjs
```

Вторая команда — отдельная проверка подготовленного артефакта; она не должна запускаться до первой. Дополнительная команда `node tests/regression/publish/artifact-negative.mjs` проверяет настоящий checker на изолированных копиях: целая сборка проходит, отсутствующий файл, сломанный импорт и служебный каталог приводят к ошибке. Общие тесты и браузерную приёмку тимлид выполняет отдельно.

Скрипт создаёт заново `dist/` (предыдущее содержимое **удаляется**). Не храните там ручные правки или единственные копии файлов. Исходную игру скрипт не изменяет. Его путь вычисляется относительно самого скрипта, а не текущего рабочего каталога.

Состав результата:

```text
dist/
  index.html
  .nojekyll
  src/
    main.js
    client/app.js
    client/input.js
    game/model.js
    game/world.js
    art/renderer.js
    art/palette.js
    art/audio.js
    art/styles.css
```

Копируется явный список фактически используемых файлов, а не весь репозиторий. Поэтому `tests/`, `research/`, `docs/`, `tools/`, `node_modules/`, `.github/`, `.git/`, конфигурация, секреты и прочие служебные файлы не попадают в публикацию. Символические ссылки отклоняются. Перед копированием проверяются существование файлов и известные литеральные ссылки HTML, JS и CSS, в том числе динамический `import('./client/app.js')`.

При добавлении нового ресурса обновите явный список в `tools/prepare-pages.mjs` после проверки его содержимого. Скрипт не является универсальным JS/HTML-парсером: вычисляемые пути и новые механизмы загрузки требуют отдельного ревью и расширения проверки. Не копируйте весь проект «для надёжности».

Результат содержит ровно 11 файлов: 10 файлов игры из списка выше и пустой `.nojekyll`. Allowlist исключает посторонние файлы, но не ищет секреты внутри разрешённых исходников: их содержимое необходимо проверить перед отправкой в GitHub.

Существующие ссылки относительные: `./src/main.js`, `./src/art/styles.css`, импорты относительно модулей. Дерево `src/` копируется без изменения путей и содержимого, без `<base>` и привязки к имени репозитория; оно рассчитано и на корень сайта, и на `/<repository>/`. Не заменяйте ссылки на `/src/...`: ведущий `/` сломает размещение в подпапке репозитория. Открытие двойным щелчком через `file://` не является корректной проверкой ES-модулей; используйте статический HTTP-хостинг.

## 2. Разрешения GitHub Pages

Владелец или администратор существующего GitHub-репозитория должен:

1. Убедиться, что Pages доступен для репозитория и его тарифа/политик организации. Если приватный репозиторий не поддерживается текущим тарифом, согласовать разрешённый вариант с владельцем; не менять видимость автоматически.
2. В **Settings → Actions → General** разрешить GitHub Actions и официальные actions, используемые workflow.
3. В **Settings → Pages → Build and deployment → Source** выбрать **GitHub Actions**. Workflow не создаёт репозиторий и не включает Pages автоматически.
4. Разрешить токену workflow `contents: read`, `pages: write`, `id-token: write` (эти permissions уже объявлены в YAML). Проверить, что ограничения организации их не запрещают. Персональный токен и секреты для стандартного Pages deployment не нужны.
5. Проверить environment **github-pages**: разрешён ли deployment выбранной ветки и требуются ли подтверждения ревьюеров. При защите окружения запуск будет ждать предусмотренного одобрения.

У пользователя, запускающего workflow, должны быть права на запуск Actions (обычно write-доступ). Доступ к настройкам Pages требует соответствующих административных прав. Ошибки 403/404 на стадии Configure/Deploy могут означать отсутствие доступа или невключённый Pages, а не дефект игры.

## 3. Ручной запуск публикации

Сначала тимлид подключает проект к GitHub через Git-панель IDE или обычный Git:

1. Выберите существующий репозиторий или создайте новый в разрешённом аккаунте/организации. Видимость согласуйте с владельцем: исходный код и содержимое публичного репозитория будут доступны отдельно от Pages-артефакта.
2. Если проект ещё не является Git-репозиторием, инициализируйте его. Проверьте список файлов перед коммитом: токены, `.env`, локальные настройки и другие секреты нельзя отправлять даже при том, что Pages копирует только allowlist.
3. Проверьте существующий remote `origin`. Если его нет, добавьте точный адрес выбранного репозитория; существующий remote не заменяйте без проверки. Используйте штатную авторизацию GitHub в IDE или Git credential manager, не записывайте токен в URL remote, команды, YAML или документацию.
4. Сделайте коммит и отправьте проверенную ревизию. В удалённом репозитории должны быть исходные файлы allowlist, `tools/prepare-pages.mjs` и `.github/workflows/pages.yml`; `dist/` коммитить не требуется. Локальные QA-проверки остаются частью исходного репозитория, но не Pages-артефакта.
5. Убедитесь, что workflow присутствует на default branch, затем выполните настройки из раздела 2. Имя default branch берите из настроек репозитория, а не предполагавайте `main` или `master`.

Наличие подключённого аккаунта или сохранённого токена в IDE само по себе не создаёт репозиторий, не отправляет файлы и не включает Pages. После подключения запуск выполняется отдельно:

1. Откройте **Actions → Publish game to GitHub Pages → Run workflow**.
2. Выберите ветку с проверенной игрой и этими файлами, затем **Run workflow**. Для появления кнопки GitHub требует присутствия `workflow_dispatch` в workflow на default branch; её имя смотрите в настройках самого репозитория.
3. Workflow проверит настройки Pages, выполнит `node tools/prepare-pages.mjs` и загрузит только подготовленный `dist/` через `actions/upload-pages-artifact@v3`. Публикация выполняется официальным `actions/deploy-pages@v4`. Перед загрузкой workflow запускает проверку `tests/regression/publish/artifact.mjs`; полный QA-прогон тимлид выполняет отдельно для публикуемой ревизии.
4. При необходимости подтвердите deployment в environment `github-pages`.
5. После успешного шага **Deploy GitHub Pages** возьмите адрес из environment **github-pages** или summary **GitHub Pages → Deployment URL**. Он получен из `steps.deployment.outputs.page_url`, а не сконструирован из имени пользователя или репозитория.

Запуск только ручной (`workflow_dispatch`); push сам по себе не публикует игру. Workflow не устанавливает зависимости и не запускает backend.

Если запуск красный, откройте **первый упавший шаг**. Подготовка сообщает отсутствующий/неразрешённый ресурс; Configure/Deploy — причину ошибки Pages. Дефекты артефакта дополнительно выявляет отдельная локальная QA-проверка из раздела 1. Дополнительное сообщение workflow напоминает про Settings → Pages, permissions и environment. Ошибку доступа должен устранять владелец репозитория, а не подмена URL. Если GitHub не вернул URL, workflow завершится ошибкой, не выдавая выдуманную ссылку.

## 4. Проверка настоящего адреса

Даже успешный deployment не заменяет проверку игры. Тимлид должен отдельно:

- Открыть **точный URL из deployment**, в том числе в приватном окне без входа в GitHub или на другом устройстве/сети. Дождаться стартового меню, начать партию.
- В DevTools → Network проверить загрузку `index.html`, CSS и всех JS-модулей: без 404, ошибочного MIME и запросов к `/src/...` в корне домена. Для project Pages запросы должны сохранять подпапку сайта.
- В Console проверить отсутствие ошибок модулей/ресурсов. Проверить перезагрузку страницы по этому же адресу.
- Проверить движение, паутину, рывок, паузу/продолжение, проигрыш, новую партию; отдельно выполнить реальное прохождение до победы. Звук проверять после пользовательского жеста. Мобильное управление и производительность не считать подтверждёнными без фактического теста.
- Зафиксировать адрес, ревизию и фактические PASS/FAIL/NOT RUN в приёмке проекта. Только после этого отправлять ссылку модерации.

Если deployment зелёный, но страница недоступна, проверьте точный URL, завершение распространения Pages, ограничения видимости и custom domain в Settings → Pages. Не объявляйте публикацию успешной только по локальному `dist/`.

## 5. Запасной вариант: itch.io

Это отдельная внешняя публикация, которую выполняет уполномоченный владелец аккаунта; скрипт и workflow её не запускают.

1. Подготовьте и проверьте `dist/` командами выше.
2. Выполните `python tools/package-itch.py`: команда повторно проверит артефакт и создаст `release/karakurt-ruka-tsela.zip`. Архив проверяется на целостность и побайтное совпадение с `dist/`. В корне ZIP лежат `index.html`, `.nojekyll` и `src/`, а не родительская папка `dist/`. Исходный репозиторий целиком не архивируется.
3. В существующем или новом проекте itch.io выберите тип **HTML** (игра запускается в браузере). Загрузите ZIP, отметьте его как запускаемый в браузере (**This file will be played in the browser**).
4. Укажите размер игрового окна **1280×720**, включите возможность fullscreen. Мобильную поддержку не обещайте до её проверки.
5. Сначала проверьте preview: меню, запуск, ввод, паузу, звук после жеста; в Console/Network iframe — отсутствие ошибок модулей и ресурсов.
6. Когда владелец готов к внешней публикации, установите публичную видимость проекта и сохраните. Откройте реальный адрес страницы itch.io без авторизации, затем запустите игру. Черновик или restricted-ссылка не являются общедоступной публикацией.

Для модерации используйте только фактически проверенную публичную ссылку Pages либо itch.io. Видео на 30 секунд можно добавить отдельно позже по правилам джема; оно не заменяет работающий адрес игры.
